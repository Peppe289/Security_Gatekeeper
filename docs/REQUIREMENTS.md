# Security Gatekeeper — Features and requirements

Security Gatekeeper is a containerized HTTP reverse proxy that exposes internal services on a
public domain. Each route is protected by a per-client rate limit and, optionally, by an API
key. Routes are managed from a web admin panel. Every request is recorded in a
tamper-evident audit log: a hash chain stored in PostgreSQL, signed with HMAC-SHA256 and
anchored outside the database.

```
https://<domain>/myservice/api/x   ──▶   http://internal-service:8080/api/x
```

---

## 1. Feature list

| # | Feature | Summary |
|---|---|---|
| F1 | Prefix-based reverse proxy | The first path segment selects the route and is stripped before forwarding |
| F2 | Route management | Create, enable/disable and delete routes from the panel; stored in PostgreSQL |
| F3 | Feature toggle | A disabled route answers 503 without contacting the upstream |
| F4 | Per-route API keys | Optional protection with a key in the `X-Api-Key` header; keys can be rotated and removed |
| F5 | Rate limiting | Token bucket per (route, client IP) pair, with configurable burst and refill rate |
| F6 | Streaming forwarding | Bodies streamed in both directions; header rewriting per RFC 9110 |
| F7 | Standard errors | Rejections returned as `application/problem+json` (RFC 9457) |
| F8 | Authenticated audit log | Every request recorded asynchronously in a hash chain signed with HMAC-SHA256 |
| F9 | Integrity verification | On-demand check of every chain, signature and anchor, from the panel |
| F10 | Audit anchors | Signed chain heads kept outside the database, to detect truncation |
| F11 | Admin panel | Server-rendered dashboard with statistics, routes and audit log |
| F12 | Machine load report | Container CPU, memory, threads, audit queue and bandwidth, with peaks and a verdict |
| F13 | Admin authentication | Form login, session, CSRF, brute-force protection |
| F14 | Multiple instances | Several nodes behind a load balancer, kept in sync through the database |
| F15 | Seed routes | Routes created from configuration on first startup |
| F16 | Health checks | Liveness and readiness endpoints for orchestrators and Docker |
| F17 | HTTPS | TLS terminated on the gateway or on an upstream load balancer |
| F18 | Container delivery | Docker image, `docker compose` stack and multi-architecture releases |

## 2. Functional requirements

### 2.1 Proxy and routing

- **FR-01** Every request whose path is outside `/_gatekeeper` must go through the proxy
  pipeline. Requests under `/_gatekeeper` go to the admin panel.
- **FR-02** The first path segment (`/{prefix}/...`) must select the route. The rest of the
  path, with the original query string, is appended to the route's target URL.
- **FR-03** A valid prefix has 1 to 63 characters from the alphabet `[a-z0-9-]` and does not
  start with `-`. If the prefix is invalid or matches no route, the gateway must answer
  **404**.
- **FR-04** The target URL must be absolute, use the `http` or `https` scheme, have a host,
  and contain no credentials, query or fragment. Maximum length: 2048 characters. A
  trailing slash is removed.
- **FR-05** The pipeline filters must run in this order: audit (wraps the whole chain) →
  route resolution → route enabled → API key → rate limit → forwarding. The first filter
  that rejects the request stops the chain.
- **FR-06** The pipeline must be extensible with custom filters, ordered with `@Order` in
  the gaps left by `FilterOrder`.

### 2.2 Route management

- **FR-07** The administrator must be able to create a route by giving its prefix, target
  URL, initial state (enabled or not), whether an API key is required, burst and
  requests per second.
- **FR-08** When burst or requests per second are not given, the configured defaults are
  used (100 and 50).
- **FR-09** Burst must be in `[1, 1,000,000]` and requests per second in
  `[1, 1,000,000,000]`.
- **FR-10** Two routes cannot share the same prefix. The panel must show a readable error.
- **FR-11** The administrator must be able to enable and disable a route. A disabled route
  answers **503** without contacting the upstream.
- **FR-12** The administrator must be able to delete a route. Its rate-limit buckets are
  removed with it.
- **FR-13** A change must update only the attribute concerned. It must not undo changes made
  meanwhile on other instances, such as a key that was just rotated.
- **FR-14** On startup the gateway must insert the configured seed routes
  (`gateway.routes.seed`), but only if the prefix does not exist yet.

### 2.3 API keys

- **FR-15** A route can require an API key. The client sends it in the configured header
  (default `X-Api-Key`).
- **FR-16** If the key is missing the gateway answers **401**; if it is wrong it answers
  **403**.
- **FR-17** The key must be generated by the system (`gk_` prefix plus 256 random bits) and
  shown to the administrator only once, with a button to copy it.
- **FR-18** The administrator must be able to protect a public route, generate a new key
  (which invalidates the previous one), and remove the key to make the route public again.
- **FR-19** The API-key header must never reach the upstream.

### 2.4 Rate limiting

- **FR-20** Each (route, client IP) pair has a token bucket whose capacity is the route's
  burst and whose refill rate is the route's requests per second.
- **FR-21** The rate limit is applied after the access checks, so rejected requests do not
  consume legitimate clients' budget.
- **FR-22** When the limit is exceeded the gateway answers **429** with a `Retry-After`
  header.
- **FR-23** Idle buckets (full again) must be removed periodically (every 60 s by default).

### 2.5 Forwarding to the upstream

- **FR-24** The request method, body and headers must be forwarded to the upstream, which
  may use `Content-Length` or `Transfer-Encoding: chunked`.
- **FR-25** Hop-by-hop headers, and any header listed in `Connection`, must be removed in
  both directions.
- **FR-26** The gateway must add or update `X-Forwarded-For` (appending the client IP),
  `X-Forwarded-Proto`, `X-Forwarded-Host` and `X-Forwarded-Prefix`.
- **FR-27** The admin panel's session cookie must be removed from the forwarded `Cookie`
  header. An upstream must not be able to set that cookie through `Set-Cookie`.
- **FR-28** Upstream redirects must be returned to the client without following them.
- **FR-29** The status, (filtered) headers and body of the upstream response must be
  returned to the client.
- **FR-30** If the upstream is unreachable the gateway answers **502**; on timeout it
  answers **504**. If the request cannot be represented upstream (invalid URI, method or
  header) it answers **400**.

### 2.6 Error responses

- **FR-31** Every rejection from the gateway must be an RFC 9457 document
  (`application/problem+json`) with `type`, `title`, `status` and `detail`, and a
  `Cache-Control: no-store` header.
- **FR-32** Error response text must be constant: it must not echo any request data.

### 2.7 Audit log

- **FR-33** Every proxied request, whether allowed, rejected or failed, must produce a
  record with: sequence, timestamp, client IP, method, path, route prefix, decision, HTTP
  status, previous hash, record hash, signing key id and MAC.
- **FR-34** The query string must never be recorded, since it may carry secrets. Paths
  longer than 512 characters are truncated.
- **FR-35** Each record must be linked to the previous one with
  `hash = SHA-256(canonical(fields) + previousHash)`. The canonical form length-prefixes
  every field, so two different records never serialize to the same string.
- **FR-36** Each record must be signed with `HMAC-SHA256(key, nodeId | hash)`. The key (at
  least 32 characters) comes from the configuration and is never stored in the database;
  its fingerprint is stored with each signature. Retired keys
  (`gateway.audit.previous-hmac-keys`) are accepted when verifying older records.
- **FR-37** Each instance (`gateway.node-id`) must write its own chain. After a restart the
  chain must resume from the last stored record.
- **FR-38** The database must reject `UPDATE`s on the audit table (trigger). `DELETE`s are
  allowed for retention policies.
- **FR-39** At most once per `gateway.audit.anchor-interval` (60 s by default), and on
  shutdown, the writer must sign the last persisted record of its chain (an *anchor*: node,
  sequence, hash, time) and write it to the log and, if `gateway.audit.anchor-dir` is set,
  append it to `<anchor-dir>/<nodeId>.anchors`.
- **FR-40** The administrator must be able to run a full verification of every chain against
  the anchors. The result reports the records and anchors checked, the number of nodes and,
  on failure, the node, the first invalid record and the reason.
- **FR-41** Verification must fail if a record breaks the hash chain, has no valid MAC (or
  one made with an unknown key), or differs from its anchor; if an anchor is not authentic,
  conflicts with another one, or refers to a record past the end of the stored chain (or to
  a chain that no longer exists); or if the configured anchor directory is missing or holds
  a malformed file.
- **FR-42** Verification must still work after retention: the remaining chain is anchored
  to its own first record, and anchors older than that record are ignored.
- **FR-43** The panel must show the latest audit records (50 by default) and the counters of
  persisted, queued and dropped records, and warn when no anchor directory is configured.

### 2.8 Admin panel

- **FR-44** The panel must live under `/_gatekeeper/` and require a login (single user, role
  `ADMIN`).
- **FR-45** The admin password comes from `GATEWAY_ADMIN_PASSWORD` and may be pre-encoded
  (`{bcrypt}…`). It is required: without it the gateway refuses to start, so no password
  is ever generated or logged.
- **FR-46** The main page must show: enabled/total routes, total requests, allowed,
  rejected, rate-limited, failed forwards and tracked clients.
- **FR-47** Every state-changing operation must be a POST followed by a redirect
  (Post/Redirect/Get), with an outcome message.
- **FR-48** Destructive actions must ask for confirmation.
- **FR-49** Times must be shown in the browser's time zone.
- **FR-50** After 5 failed logins (default) from the same IP, further attempts are blocked:
  one attempt is regained every 30 s. A successful login resets the counter.
- **FR-51** The administrator must be able to log out. Only one active session per user is
  allowed.

### 2.9 Machine load

- **FR-52** The panel must show the load of the container the gateway runs in, so the
  administrator can judge how much more traffic it can take.
- **FR-53** Every `gateway.monitoring.sample-interval` (5 s by default) the gateway must
  sample: CPU in use against the CPUs available to the container; memory in use, excluding
  the reclaimable page cache, against the container's limit (or the host's memory); JVM heap against its maximum; worker threads busy with proxied
  requests against the server's maximum (the highest count since the previous sample);
  audit events queued against the queue capacity; bytes received and sent on the container's
  non-loopback interfaces; requests handled.
- **FR-54** Samples older than `gateway.monitoring.window` (15 min by default) must be
  discarded. For each resource the panel shows the current value and the peak over the
  window, and marks it *High* from a 70% peak and *Critical* from 90%, with a text label
  next to the color.
- **FR-55** The panel must show the current, average and peak bandwidth in and out (bit/s),
  requests per second and CPU over the window, each with a trend line.
- **FR-56** The panel must summarize the load in one sentence naming the most loaded
  resource and its peak, from "plenty of headroom" to "saturated".
- **FR-57** Metrics that cannot be measured on the platform (e.g. network traffic outside
  Linux) must be shown as unavailable, never as zero.

### 2.10 Operations

- **FR-58** A health endpoint (`/_gatekeeper/health`, with liveness and readiness probes)
  must be reachable without authentication.
- **FR-59** Each instance must periodically reload routes from the database (every 10 s by
  default), so changes made on another node propagate.
- **FR-60** On shutdown the gateway must complete in-flight requests and persist the audit
  events still queued.

## 3. Non-functional requirements

### 3.1 Security

- **NFR-01** API keys must never be stored in clear: only their SHA-256 digest. Comparison
  must be constant-time.
- **NFR-02** Keys must be generated with `SecureRandom` (256 bits of entropy).
- **NFR-03** Every SQL query must be parameterized.
- **NFR-04** The panel must enforce:
  - a strict Content-Security-Policy (`'self'`, no inline scripts, `frame-ancestors 'none'`);
  - `X-Frame-Options: DENY`, `Referrer-Policy: same-origin` and a restrictive
    `Permissions-Policy`;
  - a CSRF token on every POST;
  - a session cookie that is `HttpOnly`, `SameSite=Strict`, scoped to the `/_gatekeeper`
    path, with a configurable `Secure` flag.
- **NFR-05** Templates must never output unescaped HTML (no `th:utext`). The panel must work
  without JavaScript.
- **NFR-06** Error pages must not expose stack traces, internal messages or exception names.
- **NFR-07** Gateway credentials (API key, admin session) must never reach the upstream. An
  upstream must not be able to fix the panel's session.
- **NFR-08** Login brute-force protection must use a registry separate from the proxy's.
  Proxied traffic must not be able to disable it.
- **NFR-09** Upstream TLS certificates must be validated against the JVM trust store.
- **NFR-10** Requests must pass Spring Security's HTTP firewall (path normalization,
  rejection of encoded path traversal) before reaching the pipeline.
- **NFR-11** The container must run as an unprivileged user.
- **NFR-12** Someone who can write to the database, even bypassing the trigger, but holds
  neither the HMAC key nor write access to the anchor storage, must not be able to modify,
  insert, remove or reorder audit records, or delete a chain up to its last anchor, without
  verification noticing (see section 4 for the remaining gaps).
- **NFR-13** Audit HMAC keys must never be stored in the database, logged, or included in the
  string form of the configuration. Signatures and anchors must be compared in constant
  time.

### 3.2 Performance

- **NFR-14** The routing decision must do no I/O and take no locks: a single volatile read
  of an immutable copy of the routes.
- **NFR-15** Auditing must not slow down traffic. The request thread only does a
  non-blocking enqueue; hashing and database writes happen on a dedicated thread, in
  batches (500 records or 500 ms by default).
- **NFR-16** Bodies must be streamed, never fully buffered: constant memory whatever their
  size.
- **NFR-17** Audit verification must use a server-side cursor: constant memory whatever the
  chain length.
- **NFR-18** Panel statistics are recomputed at most every 5 s (default), regardless of how
  many admins are connected. At least 30 s (default) must pass between two full audit
  verifications.
- **NFR-19** The token bucket must run in constant time without multiplications (no
  overflow), on a monotonic clock.
- **NFR-20** Load sampling must run in the background at a fixed rate and keep a bounded
  history (window / interval samples); rendering the panel only reads it. Counting the
  requests in flight adds two atomic operations per request.

### 3.3 Reliability and availability

- **NFR-21** If the database is unavailable, audit batches are retried with exponential
  backoff (from 200 ms up to 30 s). If the queue fills up (50,000 events by default), new
  events are dropped and counted, without blocking traffic.
- **NFR-22** After an audit sequence collision (batch already committed, or another instance
  using the same `node-id`), the writer must resynchronize on its own without losing events.
- **NFR-23** Rate-limiter memory must stay bounded (100,000 clients by default). Beyond the
  limit new clients are rejected (fail-closed). Inline cleanup runs at most once per second.
- **NFR-24** Upstream timeouts must be configurable (defaults: connect 5 s, response 60 s).
- **NFR-25** Shutdown must be graceful. The container must expose a `HEALTHCHECK`.

### 3.4 Scalability

- **NFR-26** Several instances must be able to run behind a load balancer, with PostgreSQL
  as the single source of truth. Per-node audit chains avoid any coordination of sequence
  numbers.
- **NFR-27** Rate limits and statistics are per instance, not shared across nodes (known
  limitation).

### 3.5 Configurability

- **NFR-28** Every setting must be overridable through environment variables and, except
  the audit HMAC key, have a safe default. Without that key the application does not start,
  rather than writing an unauthenticated audit log.
- **NFR-29** Configuration must be typed and validated at startup: an invalid value
  prevents the application from starting.

### 3.6 Maintainability and quality

- **NFR-30** The domain (`core`: token bucket, route policy, audit chain) must be plain Java,
  with no framework dependencies.
- **NFR-31** `core` classes must carry JML specifications, type-checked and statically
  verified with OpenJML in CI (blocking job).
- **NFR-32** Code coverage: a JaCoCo threshold on `core` and PiTest mutation testing with a
  blocking threshold.
- **NFR-33** Integration tests against a real PostgreSQL (Testcontainers) and a test
  upstream.
- **NFR-34** JMH benchmarks of the rate limiter, runnable on demand.
- **NFR-35** Automated security checks: secret scanning (GitGuardian), dependency and image
  scanning (Snyk), static analysis (SonarQube Cloud) and weekly Dependabot updates.
- **NFR-36** The database schema must be versioned with Flyway.

### 3.7 Portability and delivery

- **NFR-37** Runtime: Java 25 and PostgreSQL 18.
- **NFR-38** Layered multi-stage Docker image, with multi-architecture releases (amd64 and
  arm64) published to GHCR for every `v*` tag.
- **NFR-39** A local stack that starts with `docker compose up` (gateway, database and a
  sample service).

### 3.8 Usability

- **NFR-40** The panel must work without JavaScript, which is used only for confirmations,
  copying keys and local times. It must not poll in the background.
- **NFR-41** Panel error messages must be clear and must not expose internal details.

## 4. Known limitations and out of scope

- One upstream per route: no load balancing or upstream health checks.
- The audit log resists anyone who can write to the database but holds neither the HMAC
  key nor write access to the anchor storage. Whoever has the key can forge records, and
  whoever controls both the database and the anchor storage can delete the latest records
  undetected.
- Records written after the last anchor (at most `gateway.audit.anchor-interval`, 60 s by
  default) can be deleted from the end of a chain without verification noticing.
- Without `gateway.audit.anchor-dir`, anchors only reach the log: verification cannot detect
  deletions from the end of a chain, unless someone compares the logged anchors by hand.
- Removing the oldest records looks the same as retention. A node whose records were all
  purged on purpose fails verification until its anchor file is removed too.
- No WebSocket or other protocol upgrades: plain HTTP requests only.
- Rate limits and statistics are per instance, not shared across nodes.
- A single administrator account, with no multiple roles.
- API keys are meant for programmatic clients: browsers do not send custom headers.
